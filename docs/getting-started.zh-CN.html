0. 先判断要不要用

一句话：Jev 提供快速局部判断，代码保留“循环、状态、终止、验收”。 Jev 让百毫秒级 AI 判断成为可能（该量级指 README 示例 中的决策请求 计时，不是每次调用或整段任务的保证），于是“下一步”可以在运行中的循环里选出——观察任务状态、选择 下一步、执行、更新状态、继续决策——而不是等一整个慢速推理回合。

适合

  • 反复出现的局部决策，每一步都不能等一整个推理回合（基于当前任务状态的快速、聚焦判断）；
  • 需要持续操作某个环境（浏览器、设备、工位、长流程），中间还要模型判断；
  • 你担心“跑着跑着卡住 / 重复点同一个按钮 / 把模型的 DONE 当成功”；
  • 需要可回放的事件日志、明确的资源独占、进程外的崩溃隔离；
  • 主 agent 思考慢，而环境驱动必须继续跑（cognition job 异步问、不等）。

不适合

  • 一次性工具调用或纯问答；
  • 需要多环境并行写、自动规划、子 loop——第一版内核明确不做；
  • 想让模型自己规划整条流程：这里代码拥有循环，模型只在一帧里选动作。

1. 它由哪几层组成

你的宿主（pi / 自己的服务 / 调度器）
  │  管理请求：start · inspect · events · heartbeat · update · stop · respond
  ▼
host（src/jev_loop/host/，每 run 一个 worker 进程）
  │  events.jsonl 唯一真相 · 租约 · resourceKeys 独占 · cognition broker · bundle 契约
  ▼
bundle（你项目里的代码 + manifest）
  └─ ManagedController：run / snapshot / update / request_stop
       └─ 内核 Loop（可选）+ 你的环境 adapter
            observe → offer → decide → validate → execute → reduce → guard
层它负责它不负责
内核 core/ 帧绑定（候选重编号 a1..an）、执行前重新校验、四态回执、三条空转守卫、纯 reducer、verifier 独立验收、各类硬预算 模型、网络、浏览器、pi；内核只依赖策略协议
宿主 host/ 幂等 start、独占资源声明、租约与超时、append-only 事件、停止两阶段、崩溃 quarantine、cognition broker 不知道你操作的是什么环境
适配层 extensions/pi-jev.ts 把宿主接到 pi：jev_loop 工具、斜杠命令、cognition 投递、session heartbeat、TUI 独占确认 不含任何站点/设备适配器
bundle（你写） manifest + ManagedController；环境 adapter、真实证据、外部输入的释放确认 不碰事件日志、租约、资源 claim

命名提醒：jev-loop 既指单环内核，也指“内核 + 宿主 + 可选 pi 扩展”这整个包； pi 工具叫 jev_loop，技能有两个：jev-loop（运行 bundle）与 jev-bundle-creator（编写 bundle）；bundle 不是仓库里的组件，而是项目侧行为包的契约名。 现在 pi-jev 只指可选的 pi package 与扩展。

3. 路径 A：bundle 与标准 CLI（不装 pi）

bundle 是与宿主无关的标准，不是 pi 的功能。bundle 位于 <project_root>/.agents/jev-bundle/<name>/，包含 bundle.json 机器 契约与 agent 启动前阅读的 BUNDLE.md。任何有 shell 的 agent 都能创建、发现、检视、校验并 运行它；pi 只是同一运行时的可选客户端。规范性契约见 spec/bundle-standard.zh-CN.md，编写指南见 docs/bundle-authoring.zh-CN.md， .agents/jev-bundle/offline-switchboard 是完整的离线参考实现。

3.1 发现、检视与校验

uv run jev-loop bundle list                                  # 本项目里有哪些 bundle
uv run jev-loop bundle show project:offline-switchboard      # 元数据与声明项
uv run jev-loop bundle validate project:offline-switchboard  # 静态契约检查
uv run jev-loop bundle conformance project:offline-switchboard --run-tests

引用形式为 diagnostic（内建契约探针）、project:<name>、已发现的裸 名称，或项目根内的 manifest 路径。发现过程只读 JSON 与文件系统元信息：不 import、不执行、不安装依赖、 不发网络请求、也不向 bundle 内写入。conformance 用子进程探针证明这种惰性，并在带 --run-tests 时以有界超时运行 bundle 自带测试——它的运行时语义部分始终是 not_checked。

3.2 创建一个

uv run jev-loop bundle init review-notes --description "整理待审阅收件箱"

它会用随安装包分发的模板写出 .agents/jev-bundle/review-notes/，因此在检出之外的 wheel 安装中同样可用。它拒绝对已存在的目标路径写入，产物是明确的脚手架：scaffold: true、 实现前会抛错的 controller，以及离线作者测试。host 默认拒绝启动脚手架；脚手架运行只证明管路，永远 不是用户任务的证据。

3.3 用请求协议运行

printf '%s' '{"action":"start","owner_id":"my-session","idempotency_key":"task-1",
  "project_root":"'"$PWD"'","bundle":"project:offline-switchboard",
  "task":{"goal":"打开所有必需的开关"},"max_runtime_seconds":30}' | uv run jev-loop rpc

start 立即返回 run_id。之后用 inspect 与 events 读证据、用 heartbeat 续租、用 respond 应答待处理 cognition 任务、用 stop 结束。pi 之外有两件事要你自己做：CLI 不会通知你，也不会替你发 心跳。只有状态为终态、resources_released 为真、且 bundle 的 verifier 判定 satisfied，这次运行才算完成。

诚实的边界。该标准与宿主无关，任何有 shell 和 CLI 的 agent 都能使用，但本仓不 声称任何第三方产品原生实现该格式。manifest 会以你的权限加载项目代码：发现与校验是惰性的，运行 bundle 不是沙箱。声明的 authorizations、资源期望、依赖、停机意图与验证意图都是建议性的—— bundle validate 会分别标注强制项、建议声明与未检查项。

4. 路径 B：当 Python 库用（不装 pi、不联网）

先跑自带 demo 熟悉语义，三个场景分别演示“正常完成”“动作无效果后收窄候选”“可逆循环被挂起等待新信息”：

uv run jev-loop-demo --scenario clean  # 正常收敛
uv run jev-loop-demo --scenario noop   # 无效果动作 → 标死并收窄候选，继续推进
uv run jev-loop-demo --scenario cycle  # 可逆循环 → suspended / awaiting_evidence，不烧满步数

第三个场景不是失败：frame 重现且无可收窄动作时，内核直接挂起等新信息（suspended / awaiting_evidence）； 只有反复升级到上限才以 cycle_detected 结束——docs/design.zh-CN.md 的守卫表与 tests/test_guards.py 的两条测试分别覆盖这两条路径。以下是 clean 场景的实际输出：

status=succeeded stop_reason=None
steps=3 executions=2 decisions=3 world={'a': True, 'b': True}
verifications=['satisfied'] (only 'satisfied' counts as success)

该 demo 离线、使用确定性 mock 环境：不调用付费 Jev 服务，也不做任何真实业务验收。

接自己的环境，只需要实现三个角色——环境、策略、验证器：

from jev_loop import Loop, TaskSpec
from jev_loop.policies.jev import JevPolicy, default_request_fn

loop = Loop(
    task=TaskSpec(
        goal="开启深色模式",
        success_criteria=("设置页显示深色模式已开启",),
    ),
    environment=my_adapter,                       # observe / offer / execute / query / validate
    policy=JevPolicy(request_fn=default_request_fn()),   # 从进程环境读 TYPESAFE_API_KEY
    verifier=my_verifier,                         # 独立证据；不接受模型的 DONE
)
result = loop.run()
print(result.status, result.stop_reason)

这段代码是集成示意，不是可直接运行的示例：my_adapter 与 my_verifier 需要你自己提供。default_request_fn() 从进程环境读取凭据；缺失或不可用会在第一个动作之前 报错。已持有密钥的代码仍可用 http_request_fn(api_key=...) 显式注入。完整可运行用例见第 5 节。

要点：

  • 策略返回的候选 id 只在本帧有效；循环在执行前会重新校验观测 revision 与前置条件。
  • JevPolicy 每次决策发一次请求到 https://api.typesafe.ai/v1/systemone；http_request_fn 是全仓唯一碰网络的地方，便于替换成假 requester 做离线测试。
  • 环境 adapter 承诺三件事：能给什么观测、能执行哪些动作、未决操作怎么查询。内核不假设任何环境细节。

5. 配置凭据并跑一次真实 Jev 用例

快速开始 demo 与上文测试套件均离线。真实 run 需要由你自己提供的 TypeSafe / Jev API key；本节是从干净克隆走到一次真实 Jev 决策、拿到证据、并能干净停止的受支持路径。不需要私有仓、浏览器 profile 或隐藏环境。

4.1 凭据

  • 受支持的入口是环境变量 TYPESAFE_API_KEY，由 jev_loop.policies.jev 的 default_request_fn() 读取。default_request_fn(env_name=...) 可换变量名； 已持有密钥的代码仍保留 http_request_fn(api_key=...) 显式注入。
  • 库只读进程环境：不解析 .env、不查 keychain、不读其他项目配置。
  • key 缺失、空白或含无法放进 header 的字符时，会在第一个网络或环境动作之前抛出具名错误； 绝不静默降级成 mock。
  • 不要把 key 写进命令行 flag、run spec/task、bundle_config、事件、snapshot 或 cognition 消息：这些都会被持久化并回读给 agent。
export TYPESAFE_API_KEY=...      # 变量已在当前进程环境中
uv run jev-loop-doctor

# 仅当你还没有把该 key 保存在本地文件时：
cp .env.example .env && chmod 600 .env
# 若 .env 已存在，请保留它并直接编辑该文件，不要复制覆盖
uv run --env-file .env jev-loop-doctor

--env-file 接的是真实文件路径，由 uv 在命令运行前加载进进程环境；库自身不读、不解析该 文件，也不会打印其值。变量已经 export 时不需要该 flag。pi 必须从已加载该变量的进程启动—— /reload 不会重新导入 key。

4.2 离线预检（不发起网络请求）

uv run jev-loop-doctor            # 人类可读报告
uv run jev-loop-doctor --json     # 面向脚本/agent 的同一份报告
uv run jev-loop-doctor --offline  # 只查安装与运行时；不需要 key
uv run jev-loop-doctor --bundle examples/live-files/bundle.json   # 顺带检查 manifest

doctor 校验 Python ≥ 3.12、host 依赖的 Unix fcntl、endpoint / model / timeout 取值， 以及凭据是否存在。它的 JSON 标注 mode: "preflight"，并把 authentication、 connectivity、model_availability 保持为 not_checked：绿灯只是本地 配置结论，不是真实 API 验收。它绝不打印凭据的值、长度或 hash。

退出码含义
0所检查的本地配置有效
2凭据缺失、空白或无法作为 HTTP header 值使用
3非秘密配置无效，或平台不支持运行时
1未知内部错误（--json 下同样可机器读取）

4.3 可直接运行的真实参考用例（合成数据 + 真实文件系统）

examples/live-files/ 是给外部工程师的自包含参考：真实 Jev 决策请求、带固定合成文件 的本机文件系统环境，以及独立 verifier。它是参考示例，不是生产适配器，也不是 benchmark； examples/ 不会打进构建出的 wheel，请从源码克隆运行；jev-loop-doctor 随包安装，在克隆目录之外也能用。

# 变量已在当前进程环境中：
uv run python examples/live-files/run.py --max-steps 8 \
    --workspace "$(mktemp -d)/workspace"

# 或显式加载私有文件（真实路径；不要自行读取该值）：
uv run --env-file .env python examples/live-files/run.py --max-steps 8 \
    --workspace "$(mktemp -d)/workspace"
  1. 先校验配置与凭据；通过之后才创建工作区。
  2. 工作区必须是新建或空目录——非空目录或 symlink 会被拒绝；示例绝不覆盖、移动或删除不是它自己创建的内容。
  3. 每个循环步骤就是一次真实的 Jev 决策请求，候选集来自该 frame；--max-steps（默认 8）限制请求次数。
  4. 环境执行真实文件操作，循环在每一步后重新读取目录，因此无可见效果的一步会被如实记录。
  5. LiveFilesVerifier 自己重读文件系统并判定；模型的回答无法让它通过。证据写入工作区内的 verification.json（默认 <workspace>/verification.json），run 会打印工作区路径。
  6. 不会自动删除任何东西：请先复核工作区，再自行删除。

它的退出码：成功 0；凭据缺失或被服务拒绝 2；循环本身失败或验证未满足 1；配置、工作区或命令行用法错误 3。

4.4 同一个用例在 managed host 下运行

同一个 adapter 与 verifier 也可作为 bundle 运行，这条路径会真正走到租约、事件日志、停止与资源释放：

uv run jev-loop-host rpc <<'JSON'
{"action":"start","owner_id":"engineer","idempotency_key":"live-files-1",
 "project_root":"/path/to/jev-loop","bundle":"examples/live-files/bundle.json",
 "task":{"goal":"prepare the synthetic inbox"},"max_runtime_seconds":120}
JSON

key 来自显式文件时，给同一条命令加上前缀 uv run --env-file .env。

之后用 inspect / events 读状态与证据，需要时 stop。只有 terminal status、resources_released=true 且 controller.verification.verdict=satisfied 才算完成——start 返回 ok 不是证据。该 bundle 始终在 run_dir/artifacts/workspace 工作，两次 run 不可能共享目录；它的 bundle_config 只接受 model、api_url、timeout 与 max_steps（1..64，默认 8）。inspect 会报告生效的 max_steps 与实际发生的 decision_requests。

4.5 pi、OpenRouter 与其他 provider

pi-jev 不会替 Jev 读取 pi 的凭据。worker 继承 pi 进程的环境，因此请从已加载该变量的进程启动 pi：

uv run pi                     # 变量已在当前 shell 环境中
uv run --env-file .env pi     # 或显式加载私有文件；/reload 不会重新导入

慢思考始终是 pi 自己的事，在 pi 里配置。如果你的 pi 会话使用其他 provider（例如 OpenRouter）， 请在 pi 侧配置：pi 支持 /login openrouter 与 OPENROUTER_API_KEY 变量 （见 pi 仓库的 docs/providers.md、 docs/models.md）。TYPESAFE_API_KEY 只用于经 policies/jev.py 发出的 Jev 决策请求；本仓不自带其他 provider 客户端，也不读 pi 的 auth 文件。

6. 路径 C：在 pi 里用（pi-jev 扩展）

仓库根就是一个 pi package（package.json 声明了 extensions/pi-jev.ts、skills/jev-loop 与 skills/jev-bundle-creator）。本仓不负责安装 pi 本身：请按 pi 的官方安装说明安装（见 pi 仓库），确认系统里有 Python 3.12+，再从克隆目录注册这个本地 package：

git clone https://github.com/kevin-zhan/jev-loop.git   # 私有仓库：需要访问权限
cd jev-loop
pi install .            # 注册本地 package，就地引用这个克隆目录

# 可选的远端非钉版本安装（仓库私有，仍需访问权限）：
# pi install git:github.com/kevin-zhan/jev-loop

# 或者临时试一把，不写设置：
# pi -e https://github.com/kevin-zhan/jev-loop

装好后在 pi 里 /reload；它提供：

技能已改名：主技能原为 pi-jev，现为 jev-loop （/skill:jev-loop），并新增用于编写的 jev-bundle-creator。已打开的会话要执行 /reload 或重启 pi 才会更新命令列表。pi 工具接口与 jev-loop-host rpc 均未改变。

入口用途
jev_loop 工具start / list / inspect / events / update / respond / stop / release_resources / bundles / validate_bundle
/jev-runs看当前 session 拥有的 run
/jev-self-test离线跑一遍真实进程验收（认知等待期间继续推进、结束后释放输入）
/jev-stop-all交互确认后停止本 session 的全部活动 run
jev-loop skill教 agent 何时用 bundle、怎么处理 cognition、怎么验收（原名为 pi-jev）
jev-bundle-creator skill教如何用真实模板编写 bundle
  • 扩展默认用 python3；别的解释器用 JEV_LOOP_PYTHON=/path/to/python3.12 指定。
  • 扩展会把 <pkg>/src 加进子进程 PYTHONPATH，因此不需要安装 Python 包，只要系统里有 Python 3.12+。
  • 启动一个 run 时要给：bundle（项目内 manifest）、goal、inputs、resourceKeys、idempotencyKey、maxRuntimeSeconds。任务内容经 stdin 传输，不进 shell 参数。

pi package 以完整系统权限运行扩展代码。安装第三方 package 前先读源码；本仓的 bundle manifest 同样是代码信任边界，宿主只接受当前可信项目目录内的 manifest。

7. 路径 D：接自己的宿主

不依赖 pi 也能用。宿主 API 从 jev_loop.host 导出，命令行入口 jev-loop-host 提供 rpc（stdin 收一个 JSON、stdout 回一个 JSON）与内部 worker：

echo '{
  "action": "start",
  "owner_id": "engineer-or-service-id",
  "idempotency_key": "daily-check-2026-09-20",
  "project_root": "/srv/my-project",
  "bundle": "/srv/my-project/.jev/bundles/my-bundle/bundle.json",
  "task": {"goal": "检查站点并留下证据", "inputs": {"date": "2026-09-20"}},
  "resource_keys": ["browser:work-profile"],
  "max_runtime_seconds": 600
}' | uv run jev-loop-host rpc
action必须字段
startowner_id · idempotency_key · project_root · bundle · task.goal
list / inspectowner_id（+ run_id）
eventsowner_id · run_id，可选 after（游标）与 limit（≤500）
heartbeat / update / stop / respond转成对 run 的命令；respond 需 run_id · job_id · expected_job_version
release_resources仅在独立确认外部输入已释放后使用（见第 9 节）
  • 幂等：(owner_id, project_root, idempotency_key) 唯一映射一个 run，重复调用不会重启控制器。
  • 租约：非 detached run 默认 30 秒，需要你的宿主定期 heartbeat；不 heartbeat 会让 worker 请求停止并释放输入。
  • 状态在磁盘上，不在你的会话历史里：默认 ~/.local/state/jev-loop/，用 JEV_LOOP_HOME 改写。会话压缩、reload 都不会重放动作。

8. 写自己的 bundle

契约正文在 docs/pi-integration.zh-CN.md 的 “Bundle manifest” 一节；可运行的模板是 examples/bundles/switchboard/（manifest + 24 行 controller，已被 tests/test_host_service.py 真实加载）。最小清单如下。

7.1 manifest

{
  "schema_version": 1,
  "entrypoint": "controller:build",
  "python_path": ".",
  "config": {"adapter": "project-specific settings"}
}

宿主会强制校验：manifest 必须在 project_root 内、schema_version == 1、 entrypoint 形如 module:function、python_path 目录存在（相对 manifest 目录解析并插入 sys.path）。 config 要求是 JSON object（宿主会 dict(...) 后与 bundle_config 合并），字符串或数字会被拒绝。

路径不要猜。相对路径（.venv/bin/python、.env）要相对 manifest 的 python_path 解析， 而不是宿主会话的当前目录——否则换一个目录启动就失败。

7.2 controller 四个方法

def build(spec: RunSpec, services: RuntimeServices, config: dict) -> ManagedController:
    ...

class ManagedController(Protocol):
    def run(self, stop_event: threading.Event) -> ControllerResult: ...
    def snapshot(self) -> Mapping[str, Json]: ...
    def update(self, task: Mapping[str, Json], patch: Mapping[str, Json]) -> None: ...
    def request_stop(self, reason: str) -> None: ...
方法线程/时机你必须保证
runengine 线程 返回 terminal 的 ControllerResult；只有确认所有外部输入已释放时 resources_released=True，强杀子进程等不确定路径必须 False
snapshotcoordinator 线程 线程安全；只放有界、可 JSON 序列化的摘要（完整证据写 run_dir/artifacts/）
updatecoordinator 线程 只在用户显式改目标/约束时被调用；不要用它偷偷改任务
request_stopcoordinator 线程（异常收尾路径下也可能由 engine 线程调用） 线程安全、同步释放 held inputs；不得等模型或网络

已经有内核 Loop 的话，直接用 LoopController 包起来即可（on_wake、on_update、 release、snapshot_extra 是可选钩子）：

from jev_loop import Loop, TaskSpec
from jev_loop.host import LoopController

def build(spec, services, config):
    environment = MyEnvironment(config)
    loop = Loop(task=TaskSpec(goal=str(spec.task["goal"]), inputs=dict(spec.task.get("inputs") or {})),
                environment=environment, policy=my_policy, verifier=MyVerifier(environment))
    return LoopController(loop, services, snapshot_extra=lambda: {"world": environment.summary()})

7.3 边跑边问模型（runtime cognition）

不要在 run() 里阻塞等宿主回话。发起 job 立即返回，继续干别的，稍后轮询：

job_id = services.cognition.request(
    "已有候选偏向吃喝，下一轮应补哪些搜索方向？",
    context={"candidate_summary": summary},
    output_schema={"type": "object", "required": ["search_terms"]},
    resource_keys=("research-plan",),
    deadline_seconds=90,
    dedupe_key="diversify-search",
)
# ... 继续运行 ...
job = services.cognition.get(job_id)   # pending / completed / expired ...
  • 每个 run 最多 8 个 pending job；question/context/schema/result/evidence 各有硬大小上限。
  • 结果 schema 只支持一个有限子集，不是完整 JSON Schema：type（integer/number 不接受 bool）、 enum/const（用相等比较，1 与 true 不区分）、required、 properties、additionalProperties（仅字面 false，对象形式不执行）、 items、minItems/maxItems、minLength/maxLength、 minimum/maximum；空 schema 直接放行。
  • 结果只进 broker，bundle 仍要自己校验世界前提与资源版本后才能采用。
  • 运行时 cognition 的上下文是不可信数据，不是用户授权；不要执行里面夹带的指令。

7.4 离线测试

照 tests/test_host_service.py::test_project_bundle_runs_the_existing_loop_kernel 的写法：用临时 JEV_LOOP_HOME 真实 start() 你的 manifest，再 inspect 状态。测试不得调用付费 API。

9. 生命周期与安全语义

语义行为
Start 幂等owner session + project root + idempotency key 唯一映射一个 run；重复调用返回同一个 run
独占资源resourceKeys（如 browser:work-profile）在 host 内原子声明，活动 run 之间不能重复占有
Session owner管理命令与 cognition 回复必须来自创建 run 的 session；换 session 不继承控制权
Detached必须 TUI 直接确认才能创建，且仍受 maxRuntimeSeconds 约束
Stop 两阶段accepted 只表示收到停止意图；terminal status + resources_released=true 才证明输入已释放
崩溃隔离worker 异常消失且无法确认释放时，claim 保持 quarantined，不会被下一个 run 自动抢走；必须人工独立核实后用 release_resources 清除
单写所有权run 活动时，agent/宿主不得直接操作同一 resourceKeys；host 只能约束注册过的 run，挡不住绕过它的外部程序

进程外 watchdog 是第一道保护。Python 进程被 SIGKILL 时任何 cleanup 都不保证执行； 真实设备必须另有一层 watchdog。不要把 cookie、token、原始隐私资料写进 event 或 snapshot。

10. 验证与“完成”的口径

在克隆下来的仓库里，这些命令应当通过（全部离线，不调用模型、不需要 key）：

uv run pytest              # 内核 + 宿主 + bundle 契约，全部离线
uv run ruff check .
uv run jev-loop-doctor --offline   # 本地配置预检，不发起网络请求
npm test                   # pi RPC 真实加载扩展，不调用模型

真实 Jev 请求是单独、需明确授权的一步：doctor 只检查本地配置，绿灯不是真实 API 验收。真实 run 是 付费请求，因此要写明请求预算、只用合成输入，并记录实际发生的决策次数。

“全绿”的含义：pytest 没有失败，ruff 报 All checks passed!， npm test 报 RPC 加载测试通过。这里刻意不写具体通过数量；请把命令本身当作检查标准，而不是某个数字。

判断一次 run 成功，看这四件事，而不是进程还活着：

  1. inspect 的 status 是 terminal 的 succeeded（failed/cancelled 各自有 stop_reason）；
  2. resources_released: true；
  3. bundle 自己的证据（run_dir/artifacts/）里 verifier 给出 satisfied；
  4. 事件日志 events.jsonl 能解释它是怎么走到这一步的。

“工具调用返回了” ≠ “动作生效了” ≠ “任务完成了”。内核把这三件事分别记录：动作回执四态 completed / rejected / pending / unknown；request_finish 只是请求验证，只有 verifier 的 satisfied 才算成功，unknown 保持 unknown。

11. 常见坑

  • 不要猜凭据该放哪。受支持的来源是进程环境里的 TYPESAFE_API_KEY （在 shell 里 export，或用 --env-file .env 让 uv 加载私有文件）；放进 task、bundle_config、事件或 cognition 消息里等于把它持久化。缺 key 会在第一个动作前失败，修好环境后请以新的 idempotency_key 重新 start——复用同一个 key 会返回旧的失败 run。
  • 加载 key 后要重启 pi。/reload 只是重载扩展，不会把另一个 shell 的环境变量导进来。
  • 不要为了“更顺畅”移除守卫（无效果 / 重复 / 循环）。确定性策略下它们是唯一的逃生阀：一步要么改变帧，要么停下来。
  • 别把模型的 DONE 当验收：策略只能 request_finish，verifier 才说了算。
  • pending / unknown 只许查询，不许重发；idempotency=NONE 的动作永远不能盲目重试。
  • 帧绑定：只能返回本帧的候选 id，不要自己拼动作名或 URL；内核会拒绝越权候选。
  • dead_actions 作用域是当前观测：观测一变就清空，别在外面自己维护“永久黑名单”。
  • 候选覆盖问题内核发现不了：正确动作不在候选集里，只能靠 adapter 与评测；内核提供 complete 标记与 blocked 出口。
  • 观测有延迟：动作效果晚于观测会被判一次 no-effect 并标死；这是有意的保守策略，效果出现后会自动回到候选集。
  • 第一版只支持单环境、单写执行；同一 resourceKeys 想并行写请先拆成不同资源。
