0. Decide whether you need it

In one sentence: Jev supplies the fast local judgment; code keeps the loop, the state, the termination and the acceptance. Jev makes hundred-millisecond-scale AI judgments practical (decision-request timing measured in the README example, not a per-call or whole-task guarantee), so the next step can be chosen inside the running loop — observe the task state, choose the next action, execute it, update the state, decide again — instead of waiting for a full slow reasoning turn.

A good fit

  • Repeated local decisions where each choice should not wait for a full reasoning turn (fast, focused judgments over the current task state);
  • An environment has to keep being operated (browser, device, workstation, long process) while the model still makes judgments;
  • You worry about "it gets stuck, clicks the same button again, or treats the model's DONE as success";
  • You need a replayable event log, explicit resource exclusivity and crash isolation outside the process;
  • The main agent thinks slowly while the environment driver must keep running (cognition jobs are asked asynchronously and are not waited on).

Not a good fit

  • One-off tool calls or plain questions and answers;
  • Multi-environment parallel writes, automatic planning or sub-loops — the first kernel version explicitly does not do them;
  • Letting the model plan the whole flow: here code owns the loop and the model chooses an action inside one frame.

Naming note: jev-loop refers both to the single-loop kernel and to the whole package (kernel + host + optional pi extension); the pi tool is called jev_loop and the skills are jev-loop (run one) and jev-bundle-creator (write one); a bundle is not a component in this repository — it is the contract name for a project-side behavior package. pi-jev now names only the optional pi package and extension.

3. Path A: bundles and the standard CLI (no pi)

Bundles are a host-neutral standard, not a pi feature. A bundle lives in <project_root>/.agents/jev-bundle/<name>/ with a bundle.json machine contract and a BUNDLE.md an agent reads before starting it. Any agent with a shell can create, discover, inspect, validate and run one; pi is an optional client of the same runtime. The normative contract is spec/bundle-standard.md, the authoring guide is docs/bundle-authoring.md, and .agents/jev-bundle/offline-switchboard is a complete offline reference.

3.1 Discover, inspect and validate

uv run jev-loop bundle list                                  # bundles in this project
uv run jev-loop bundle show project:offline-switchboard      # metadata and declarations
uv run jev-loop bundle validate project:offline-switchboard  # static contract check
uv run jev-loop bundle conformance project:offline-switchboard --run-tests

References are diagnostic (the built-in contract probe), project:<name>, a bare discovered name, or a manifest path inside the project root. Discovery reads JSON and filesystem metadata only: no import, no execution, no dependency install, no network request and no write inside a bundle. conformance proves that inertness with a child-process probe and, with --run-tests, runs the bundle's own tests under a bounded timeout — its runtime-semantics section stays not_checked.

3.2 Create one

uv run jev-loop bundle init review-notes --description "triage the review inbox"

That writes .agents/jev-bundle/review-notes/ from templates shipped inside the installed package, so it also works from a wheel outside this checkout. It refuses to touch an existing target path, and the result is explicitly a scaffold: scaffold: true, a controller that raises until implemented, and offline author tests. The host refuses to start a scaffold by default; a scaffold run would prove plumbing only, never a user task.

3.3 Run one through the request protocol

printf '%s' '{"action":"start","owner_id":"my-session","idempotency_key":"task-1",
  "project_root":"'"$PWD"'","bundle":"project:offline-switchboard",
  "task":{"goal":"turn on every required switch"},"max_runtime_seconds":30}' | uv run jev-loop rpc

start returns immediately with a run_id. Then inspect and events for evidence, heartbeat to renew the lease, respond to answer a pending cognition job, and stop to end it. Two duties are yours outside pi: the CLI does not notify you and does not heartbeat for you. A run is finished only when its status is terminal, resources_released is true and the bundle's verifier says satisfied.

Honest limits. The standard is host-neutral and any agent with a shell and the CLI can use it, but no third-party product is claimed to implement the format natively. A manifest loads project code with your privileges: discovery and validation are inert, running a bundle is not a sandbox. Declared authorizations, resource expectations, dependencies, stop intent and verification intent are advisory — bundle validate marks enforced, advisory and not-checked separately.

4. Path B: as a Python library (no pi, no network)

Start with the built-in demo to get a feel for the semantics: the three scenarios show "a normal finish", "an action with no effect narrows the candidate set", and "a reversible cycle is suspended to wait for new information".

uv run jev-loop-demo --scenario clean  # converges normally
uv run jev-loop-demo --scenario noop   # a no-effect action is marked dead, the candidate set narrows, progress continues
uv run jev-loop-demo --scenario cycle  # a reversible cycle is suspended (awaiting_evidence) instead of burning the step budget

The third scenario is not a failure: when the frame reappears and no action can be narrowed, the kernel suspends directly and waits for new information (suspended / awaiting_evidence); only when escalations repeatedly hit the limit does it end with cycle_detected. The guard table in docs/design.md and two tests in tests/test_guards.py cover these two paths. This is exactly what the clean scenario prints:

status=succeeded stop_reason=None
steps=3 executions=2 decisions=3 world={'a': True, 'b': True}
verifications=['satisfied'] (only 'satisfied' counts as success)

The demo is offline and uses the deterministic mock environment: it calls no paid Jev service and does not validate any real business task.

To connect your own environment you implement three roles — environment, policy, verifier:

from jev_loop import Loop, TaskSpec
from jev_loop.policies.jev import JevPolicy, default_request_fn

loop = Loop(
    task=TaskSpec(
        goal="Turn on dark mode",
        success_criteria=("the appearance page reports dark mode as enabled",),
    ),
    environment=my_adapter,                       # observe / offer / execute / query / validate
    policy=JevPolicy(request_fn=default_request_fn()),   # TYPESAFE_API_KEY from the process env
    verifier=my_verifier,                         # independent evidence; ignores the model's DONE
)
result = loop.run()
print(result.status, result.stop_reason)

This is an integration sketch, not a standalone runnable example: my_adapter and my_verifier are yours to provide. default_request_fn() reads the credential from the process environment and fails before the first action when it is missing or unusable; code that already holds a secret keeps the explicit http_request_fn(api_key=...) injection point. A complete runnable case is in section 5.

Key points:

  • A candidate id returned by a policy is valid only inside its frame; before execution the loop re-checks the observation revision and the preconditions.
  • JevPolicy sends one request per decision to https://api.typesafe.ai/v1/systemone; http_request_fn is the only place in the repository that touches the network, which makes it easy to swap in a fake requester for offline tests.
  • An environment adapter promises three things: which observations it can produce, which actions it can execute, and how unresolved operations are queried. The kernel assumes nothing about the environment.

5. Configure credentials and run a real Jev case

The quick-start demo and the test suite above are offline. A live run needs a TypeSafe/Jev API key that you provide; this section is the supported path from a clean clone to a real Jev decision, its evidence and a clean stop. It needs no private repository, no browser profile and no hidden environment.

4.1 Credential

  • The supported entry point is the environment variable TYPESAFE_API_KEY, read by default_request_fn() in jev_loop.policies.jev. default_request_fn(env_name=...) accepts another name, and code that already holds a secret keeps the explicit http_request_fn(api_key=...) injection.
  • The library reads the process environment only: no .env parsing, no keychain lookup, no other project's configuration.
  • A missing, blank or header-unsafe key raises a named error before the first network or environment action; there is no silent fallback to a mock.
  • Never put the key in a command-line flag, a run spec/task, bundle_config, an event, a snapshot or a cognition message: those are persisted and read back by agents.
export TYPESAFE_API_KEY=...      # the variable is already in this process environment
uv run jev-loop-doctor

# only if you do not already keep this key in a local file:
cp .env.example .env && chmod 600 .env
# if .env already exists, keep it and edit that file instead of copying over it
uv run --env-file .env jev-loop-doctor

--env-file takes a real file path and lets uv load it into the process environment before the command runs; nothing in the library reads or parses that file, and the value is never printed. Whenever the variable is already exported, the flag is unnecessary. pi must be started from a process that already has it — /reload does not re-import the key.

4.2 Offline preflight (no network request)

uv run jev-loop-doctor            # human report
uv run jev-loop-doctor --json     # the same report for scripts and agents
uv run jev-loop-doctor --offline  # installation/runtime check; no key required
uv run jev-loop-doctor --bundle examples/live-files/bundle.json   # also check the manifest

The doctor checks Python ≥ 3.12, the host's Unix fcntl requirement, the endpoint, model and timeout values, and whether the credential is present. Its JSON reports mode: "preflight" and keeps authentication, connectivity and model_availability as not_checked: a green report is a local configuration statement, not a live-API verification. It never prints the credential's value, length or hash.

Exit codeMeaning
0The checked local configuration is valid
2Credential missing, blank or unusable as an HTTP header value
3Invalid non-secret configuration, or a platform that cannot host the runtime
1Unexpected internal error (also machine-readable with --json)

4.3 Runnable live example (synthetic data, real filesystem)

examples/live-files/ is a self-contained reference for an external engineer: real Jev decision requests, a real local filesystem environment with fixed synthetic files, and an independent verifier. It is a reference example, not a production adapter and not a benchmark; examples/ is not part of the built wheel, so run it from the source clone, while jev-loop-doctor is installed with the package and also works outside a checkout.

# the variable is already in this process environment:
uv run python examples/live-files/run.py --max-steps 8 \
    --workspace "$(mktemp -d)/workspace"

# or load a private file explicitly (a real path; never read the value yourself):
uv run --env-file .env python examples/live-files/run.py --max-steps 8 \
    --workspace "$(mktemp -d)/workspace"
  1. Configuration and credential are validated first; the workspace is created only after that.
  2. The workspace must be new or empty — a non-empty directory or a symlink is refused, and the example never overwrites, moves or deletes anything it did not create itself.
  3. Each loop step is one real Jev decision request over the candidates offered in that frame; --max-steps (default 8) bounds the number of requests.
  4. The environment performs real file operations and the loop re-reads the directory after each step, so a step with no visible effect is recorded as such.
  5. LiveFilesVerifier re-reads the filesystem and decides; the model's answer cannot make it pass. Evidence is written to verification.json inside the workspace (default <workspace>/verification.json), whose path the run prints.
  6. Nothing is deleted automatically: review the workspace, then remove it yourself.

The runner exits 0 on success, 2 when the credential is missing or the service rejected it, 1 when the loop itself failed or verification stayed unsatisfied, and 3 for a configuration, workspace or command-line usage error.

4.4 The same example under the managed host

The same adapter and verifier also run as a bundle, which is the path that exercises leases, event journal, stop and resource release:

uv run jev-loop-host rpc <<'JSON'
{"action":"start","owner_id":"engineer","idempotency_key":"live-files-1",
 "project_root":"/path/to/jev-loop","bundle":"examples/live-files/bundle.json",
 "task":{"goal":"prepare the synthetic inbox"},"max_runtime_seconds":120}
JSON

When the key comes from an explicit file, prefix the same command with uv run --env-file .env.

Then read inspect / events and stop with stop. A run counts as done only when the status is terminal, resources_released is true and controller.verification.verdict is satisfied — start returning ok is not evidence. The bundle always works in run_dir/artifacts/workspace, so two runs can never share a directory, and its bundle_config accepts only model, api_url, timeout and max_steps (1..64, default 8). inspect reports the effective max_steps and the decision_requests actually made.

4.5 pi, OpenRouter and other providers

pi-jev does not read pi's credentials for Jev. The worker inherits the environment of the pi process, so start pi from a process where the variable is already loaded:

uv run pi                     # the variable is already exported in this shell
uv run --env-file .env pi     # or load a private file explicitly; /reload does not re-import it

Slow reasoning stays a pi concern configured in pi itself. If your pi session uses another provider — OpenRouter, for example — configure it there: pi supports /login openrouter and the OPENROUTER_API_KEY variable (see docs/providers.md and docs/models.md in the pi repository). TYPESAFE_API_KEY is only for Jev decision requests through policies/jev.py; this repository ships no other provider client and reads none of pi's auth files.

6. Path C: inside pi (the pi-jev extension)

The repository root is itself a pi package (package.json declares extensions/pi-jev.ts, skills/jev-loop and skills/jev-bundle-creator). Pi itself is not installed by this repository: install it using its official installation instructions (see the pi repository), make sure Python 3.12+ is available, then register this local package from the clone:

7. Path D: attach your own host

pi is not required. The host API is exported from jev_loop.host, and the command-line entry point jev-loop-host offers rpc (one JSON in on stdin, one JSON out on stdout) plus the internal worker:

echo '{
  "action": "start",
  "owner_id": "engineer-or-service-id",
  "idempotency_key": "daily-check-2026-09-20",
  "project_root": "/srv/my-project",
  "bundle": "/srv/my-project/.jev/bundles/my-bundle/bundle.json",
  "task": {"goal": "Check the site and leave evidence", "inputs": {"date": "2026-09-20"}},
  "resource_keys": ["browser:work-profile"],
  "max_runtime_seconds": 600
}' | uv run jev-loop-host rpc
actionRequired fields
startowner_id · idempotency_key · project_root · bundle · task.goal
list / inspectowner_id (+ run_id)
eventsowner_id · run_id, optional after (cursor) and limit (≤500)
heartbeat / update / stop / respondTurned into commands for a run; respond needs run_id · job_id · expected_job_version
release_resourcesOnly after independently confirming that external inputs were released (see section 9)
  • Idempotency: (owner_id, project_root, idempotency_key) maps to exactly one run; a repeated call does not restart the controller.
  • Lease: non-detached runs default to 30 seconds and need regular heartbeats from your host; without them the worker requests a stop and releases its inputs.
  • State is on disk, not in your session history: by default ~/.local/state/jev-loop/, overridable with JEV_LOOP_HOME. Compaction and reloads never replay actions.

8. Write your own bundle

The contract text is the "Bundle manifest" section of docs/pi-integration.md; the runnable template is examples/bundles/switchboard/ (a manifest plus a 24-line controller, really loaded by tests/test_host_service.py). The minimal checklist follows.

7.1 Manifest

{
  "schema_version": 1,
  "entrypoint": "controller:build",
  "python_path": ".",
  "config": {"adapter": "project-specific settings"}
}

The host enforces: the manifest must be inside project_root, schema_version == 1, entrypoint shaped like module:function, and the python_path directory must exist (resolved relative to the manifest directory and inserted into sys.path). config must be a JSON object (the host does dict(...) and merges it with bundle_config); strings or numbers are rejected.

Do not guess paths. Relative paths (.venv/bin/python, .env) must be resolved relative to the manifest's python_path, not the host session's current directory — otherwise starting from another directory fails.

7.2 The four controller methods

def build(spec: RunSpec, services: RuntimeServices, config: dict) -> ManagedController:
    ...

class ManagedController(Protocol):
    def run(self, stop_event: threading.Event) -> ControllerResult: ...
    def snapshot(self) -> Mapping[str, Json]: ...
    def update(self, task: Mapping[str, Json], patch: Mapping[str, Json]) -> None: ...
    def request_stop(self, reason: str) -> None: ...
MethodThread/timingWhat you must guarantee
runengine thread Returns a terminal ControllerResult; resources_released=True only after confirming all external inputs are released — uncertain paths such as force-killing a child process must be False
snapshotcoordinator thread Thread-safe; only a bounded, JSON-serializable summary (full evidence goes to run_dir/artifacts/)
updatecoordinator thread Only called when the user explicitly changes the goal/constraints; do not use it to change the task secretly
request_stopcoordinator thread (may also be called by the engine thread during abnormal shutdown) Thread-safe, releases held inputs synchronously; must not wait for a model or the network

If you already have a kernel Loop, wrap it in LoopController (on_wake, on_update, release and snapshot_extra are optional hooks):

from jev_loop import Loop, TaskSpec
from jev_loop.host import LoopController

def build(spec, services, config):
    environment = MyEnvironment(config)
    loop = Loop(task=TaskSpec(goal=str(spec.task["goal"]), inputs=dict(spec.task.get("inputs") or {})),
                environment=environment, policy=my_policy, verifier=MyVerifier(environment))
    return LoopController(loop, services, snapshot_extra=lambda: {"world": environment.summary()})

7.3 Asking the model while running (runtime cognition)

Do not block inside run() waiting for the host to answer. Requesting a job returns immediately; keep working and poll later:

job_id = services.cognition.request(
    "Existing candidates lean toward food and drink; which search directions should the next round add?",
    context={"candidate_summary": summary},
    output_schema={"type": "object", "required": ["search_terms"]},
    resource_keys=("research-plan",),
    deadline_seconds=90,
    dedupe_key="diversify-search",
)
# ... keep running ...
job = services.cognition.get(job_id)   # pending / completed / expired ...
  • Each run has at most 8 pending jobs; question/context/schema/result/evidence each have hard size limits.
  • The result schema supports only a limited subset, not full JSON Schema: type (integer/number do not accept bool), enum/const (compared for equality, 1 and true are not distinguished), required, properties, additionalProperties (literal false only; the object form is not executed), items, minItems/maxItems, minLength/maxLength, minimum/maximum; an empty schema passes everything.
  • Results only reach the broker; a bundle still has to validate its world preconditions and resource versions before adopting one.
  • Runtime cognition context is untrusted data, not user authorization; do not execute instructions smuggled inside it.

7.4 Offline testing

Follow tests/test_host_service.py::test_project_bundle_runs_the_existing_loop_kernel: use a temporary JEV_LOOP_HOME and really start() your manifest, then inspect the state. Tests must not call paid APIs.

9. Lifecycle and safety semantics

SemanticsBehavior
Idempotent startowner session + project root + idempotency key maps to one run; a repeated call returns the same run
Exclusive resourcesresourceKeys (for example browser:work-profile) are declared atomically inside the host; active runs cannot hold the same one
Session ownerManagement commands and cognition replies must come from the session that created the run; a different session does not inherit control
DetachedCan only be created with direct TUI confirmation, and is still bounded by maxRuntimeSeconds
Two-phase stopaccepted only means the stop intent was received; terminal status + resources_released=true is what proves the inputs were released
Crash isolationWhen a worker disappears without a confirmable release, the claim stays quarantined and is not taken over automatically by the next run; a human must independently verify and then clear it with release_resources
Single-writer ownershipWhile a run is active, no agent/host may operate the same resourceKeys directly; the host can only constrain registered runs and cannot stop an external program from bypassing it

An out-of-process watchdog is the first line of protection. No cleanup is guaranteed when a Python process is SIGKILLed; a real device needs another watchdog layer. Never write cookies, tokens or raw private data into events or snapshots.

10. Verification and what "done" means

These commands should pass in the cloned repository (all offline; no model calls, no API key):

uv run pytest              # kernel + host + bundle contract, all offline
uv run ruff check .
uv run jev-loop-doctor --offline   # local configuration preflight, no network request
npm test                   # real pi RPC load of the extension, no model calls

Live Jev requests are a separate, explicitly authorized step: the doctor only checks local configuration, and its green report is not a live-API verification. A live run is a real paid request, so state the request budget, use synthetic inputs, and record how many decisions were made.

A green run means: pytest reports no failures, ruff reports All checks passed!, and npm test reports the RPC load test passing. The exact counts are deliberately not pinned here; treat the commands, not a number, as the check.

Judge a run by these four things, not by whether the process is still alive:

  1. inspect's status is the terminal succeeded (failed/cancelled each carry their own stop_reason);
  2. resources_released: true;
  3. the bundle's own evidence (under run_dir/artifacts/) contains a verifier verdict of satisfied;
  4. the event log events.jsonl explains how it got there.

"The tool call returned" ≠ "the action took effect" ≠ "the task is done". The kernel records these three separately: a receipt has four states completed / rejected / pending / unknown; request_finish only requests verification, only the verifier's satisfied counts as success, and unknown stays unknown.

11. Common pitfalls

  • Do not guess where the credential goes. The supported source is TYPESAFE_API_KEY in the process environment (export it in the shell, or let uv load a private file with --env-file .env); putting it in a task, bundle_config, an event or a cognition message persists it. A missing key fails before the first action, so fix the environment and start a new run — reusing the same idempotency_key returns the old failed run.
  • Restart pi after loading the key. /reload reloads the extension; it does not re-import environment variables from another shell.
  • Do not remove the guards (no-effect / repeat / cycle) to "make the loop smoother". For a deterministic policy they are the only escape valves: a step either changes the frame or stops.
  • Do not accept the model's DONE: a policy can only request_finish; the verifier decides.
  • pending / unknown may only be queried, never resent; an action with idempotency=NONE is never retried blindly.
  • Frame binding: return only candidate ids from the current frame; do not piece together action names or URLs yourself — the kernel rejects unauthorized candidates.
  • dead_actions are scoped to the current observation: they clear when the observation changes; do not keep a "permanent blacklist" outside the kernel.
  • The kernel cannot detect candidate-coverage gaps: if the right action is not in the candidate set, only the adapter and evaluation can catch it; the kernel offers a complete flag and a blocked exit.
  • Observations can lag: an effect that arrives after the observation is counted as one no-effect step; this is deliberately conservative, and the action returns to the candidate set once the effect shows up.
  • The first version supports one environment and single-writer execution only; to write in parallel, split into different resourceKeys first.
